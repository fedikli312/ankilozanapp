# Project Memory

## Stable product facts
- Product: Ankilozanapp (working title)
- Target user: Adults diagnosed with ankylosing spondylitis (AS) or axial spondyloarthritis (axSpA)
- Core job: Remember and organize what happens between rheumatology appointments — medications, injections, symptoms, labs, appointments, and reminders in one place
- Business model: Undecided (see PROJECT_CONTEXT.md)

## Current architecture
- Expo SDK: Not yet installed (Expo Router + TypeScript strict + EAS approved direction; exact versions confirmed at scaffold time — see `docs/TECHNICAL_ARCHITECTURE.md`)
- React Native: Not yet installed
- Navigation: Expo Router approved
- Local database: expo-sqlite approved as V1 source of truth (local-first); drizzle-orm used if compatibility confirmed at scaffold time, else raw-expo-sqlite fallback — not yet installed
- Data access: strict layering approved — UI → feature/application services → domain logic → repositories → SQLite; UI/screens never query SQLite directly
- Backend: Supabase explicitly deferred — no auth, sync engine, cloud schema, remote repositories, or account UI in V1
- Localization: expo-localization + i18n-js + native Intl, locales en/tr, approved — not yet installed
- Subscriptions: None in V1; architecture to remain RevenueCat-compatible
- Analytics: None in V1 — no analytics or crash-reporting SDK

## Protected behavior
Established by the Phase 0–7 foundation build, enforced by automated tests — must not regress:
- Medication/injection administration immutability: `scheduledFor`/history are never rewritten when a schedule changes (`src/repositories/__tests__/medication.test.ts`, `src/domain/scheduling/__tests__/scheduleVersioning.test.ts`).
- Schedule versioning: editing a schedule supersedes the old version and inserts a new one, never mutates in place.
- Injection next-date calculation anchors to the actual logged date, not the original schedule, so early/late logging doesn't silently drift.
- Notification default copy stays generic/privacy-preserving unless both `detailOptIn` and a detailed body are explicitly supplied.
- One check-in per calendar day, editable same-day via upsert.
- 14-day upcoming-appointment window and 8-occurrence custom-interval reminder window stay as named domain constants, not per-screen literals.

Established by the Phase 8–10 build (2026-08-26), also enforced by automated tests:
- Notification permission is requested only when a medication/injection is saved with its reminder toggle on — never at app launch, never speculatively (`src/features/medications/__tests__/medicationReminders.test.ts`, `src/features/injections/__tests__/injectionReminders.test.ts`).
- Editing a medication's schedule prunes only still-`pending` (not-yet-occurred) doses from the superseded version and never touches a recorded (taken/missed/skipped) administration.
- Injection reschedule never marks the moved occurrence as missed and never alters the recurring interval.
- `generateDueAdministrations` never creates a duplicate row for a date/time pair that already has one, even when called repeatedly (Today's own reconciliation-on-focus).
- Onboarding completion is a singleton, idempotent write — re-running it updates the one row rather than creating a second (`src/repositories/__tests__/onboarding.test.ts`).

Established by the Phase 11–17 build (2026-08-28), also enforced by automated tests:
- Appointment reminder reconciliation always cancels-then-recreates on edit, never leaves a stale notification (`src/features/appointments/__tests__/appointmentReminders.test.ts`).
- `runReconciliation` never calls `requestNotificationPermissionAsync` — only reads current permission status and skips scheduling work when it isn't granted (`src/features/reconciliation/__tests__/runReconciliation.test.ts`).
- Custom-interval medication reminder top-up never re-schedules a date that's already bookkept, and correctly drops past-dated occurrences from the "still needed" count on each pass.
- Medication/injection/appointment notification content only includes a name when `UserPreferences.notificationDetailOptIn` is explicitly true — default stays generic.

Established by the 2026-08-28 full V1 review pass, also enforced by automated tests:
- Appointment cancel never hard-deletes — the row survives with `status: "cancelled"` and moves from upcoming into the past list (`src/repositories/__tests__/appointment.test.ts`).
- `deleteAllLocalData` clears every table, including `onboarding_state` and `user_preferences` — verified with one seeded row per table (`src/repositories/__tests__/dataManagement.test.ts`).
- Lab result edit/delete work as plain corrigible operations with no write-once restriction (`src/repositories/__tests__/labAndNotifications.test.ts`).

Established by the 2026-08-28 check-in-notes gap closure, also enforced by automated tests:
- Same-day check-in upsert both updates and clears an optional note correctly — an update that omits `notes` explicitly nulls the column rather than silently retaining the previous value (`src/repositories/__tests__/checkIn.test.ts`).
- Appointment Preparation's recorded-notes list includes every non-empty check-in note within the resolved lookback range (inclusive of both boundary dates) and excludes notes outside it, regardless of `flagged_important` (`src/features/appointmentPreparation/__tests__/useAppointmentPreparation.test.ts`).
